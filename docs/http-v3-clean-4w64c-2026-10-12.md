# HTTP V3 clean-host rerun: 4 workers, 64 connections

This V3 loopback run completed after the earlier conntrack saturation screens. It used the same prepared Forge and Rust HTTP server fixtures and a single pinned epoll client reactor. The run completed eight paired measurements per implementation at 32-byte bodies and 64 concurrent sockets. Each measurement issued 4,000 fresh-connection requests; all 16 measurements completed all requests with exact response bytes, EOF, and zero errors (64,000 total successful requests across both implementations, including warmups excluded from that total).

| Measure | Forge | Rust | Interpretation |
| --- | ---: | ---: | --- |
| Median throughput | 8,591.7 req/s | 8,556.6 req/s | Per 4,000-request measurement |
| Paired Rust/Forge throughput ratio | — | 1.0046 [0.7070, 1.0254] | Broad 95% bootstrap interval; no 10% advantage established |
| Largest configured simultaneous sockets in this run | 64 | 64 | All requests succeeded; this is a tested point, not maximum capacity |
| Errors / incomplete requests | 0 | 0 | Across all 16 measured samples |

The client reactor was pinned to one CPU and spent about 0.40–0.46 seconds in system time during most 0.4–0.5 second samples. This indicates that the observer was close to saturating its core. Consequently, these end-to-end loopback rates do not establish server-only throughput or maximum accepted clients. The paired interval is also wide and includes parity. V3 results are not compatible with V1/V2 and must not be pooled with them.

The prior V2 evidence remains the largest tested burst: four one-request-per-lane bursts at 28,000 configured clients. That is also a tested point, not an absolute capacity limit. Establishing maximum capacity or server-only requests per second requires an observer that does not bottleneck on a single client core, ideally from a separate host, with controlled network state and a stepped concurrency/load profile.
