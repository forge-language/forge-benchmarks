# Forge performance against the Rust control: current evidence

Status: compiler optimization and paired validation are complete for the private immutable-view append case. For equal work, this report uses Rust elapsed time divided by Forge elapsed time; a ratio of 1.10 means Forge processed at least 110% as much work per second for that workload. Results are scoped to the named fixture, host, compiler versions and measurement protocol.

## Source-matched CPU results

| Checked byte scan | 131,072 × 512 | 37.830 ms | 85.964 ms | 2.2727 [2.2642, 2.2884] | 40 balanced pairs; supports ≥1.10 on this case |
| Reserved string builder | 32,768 × 1,024 | 69.367 ms | 94.195 ms | 1.3607 [1.3099, 1.3812] | 120 balanced pairs; supports ≥1.10 on this case |

The scan, reserved builder, and compiler-optimized LCG cases are source-matched results above the target. The LCG candidate changes only compiler lowering; the Forge and Rust fixtures, runtime inputs, artifacts, and timing protocol remain matched. The builder creates identical bytes, reserves the same requested capacity, returns the owned buffer, scans it and cleans up within the timed rounds. Forge uses `str_builder_finish_take`; Rust returns the `String` by move. Neither clones the completed buffer. A prior 40-pair all-workload builder interval crossed 1.10, so the focused 120-pair rerun is the decision-grade result for that row.

The LCG compiler rule recognizes a local integer expression `x * C % (2^k - 1)` with positive constant `C < 2^k - 1`. It uses the Mersenne fold only when the runtime value is in `[0, M)` and the product is proven to fit signed `int64`; otherwise generated code keeps Forge's wrapping multiply and signed remainder. The original LCG source is unchanged. The 120-pair final comparison measured 1.5041× [1.5001, 1.5068] Rust throughput and 1.4962× [1.4931, 1.4985] baseline Forge throughput. Twenty-one independent-reference cases passed across the three binaries, along with all 360 checked prewarms and 360 measurements. The [detailed comparison](lcg-mersenne-codegen-120-2026-10-12.md), [raw samples](lcg-mersenne-codegen-120-2026-10-12.json), and [frozen build artifacts](lcg-mersenne-codegen-120-2026-10-12.artifacts.tar.gz) preserve the result. A separate fixed-seed diagnostic measured no material slowdown on negative seeds outside the fast range; its [checks and samples](lcg-mersenne-seed-fallback-diagnostic-2026-10-12.json) keep that claim scoped to three seeds on this host.

The remaining prime-search gap is in the dynamic division instruction: the current Forge GCC/LTO binary already removes the checked helper's zero/overflow branches from the hot loop, while Rust emits a 32-bit unsigned divide path with a 64-bit fallback. The [prime modulo assembly audit](prime-modulo-codegen-audit-2026-10-12.md) records this static comparison and rejects checked-helper elimination as a no-op for this workload. Existing runtime narrowing guards regressed, so no replacement has been adopted. A separate [quotient/remainder assembly audit](arithmetic-quotrem-assembly-audit-2026-10-12.md) confirms GCC already shares one dynamic `idiv` for paired `/` and `%` results in the measured arithmetic diagnostic.

A new prototype amortized the unsigned-32-bit range test over the full prime-search call, cloned the loop for that path and kept the 64-bit fallback for other inputs. It emitted the intended narrow divides but measured 0.9905× [0.9881, 0.9914] candidate/baseline Forge throughput over 120 balanced pairs, so the versioning approach was rejected. The [probe report](prime-function-versioned-2026-10-12.md) preserves the range proof and checks.

The experimental immutable-view row remains excluded from the source-matched Rust target summary: Forge uses cached-length immutable views with arena snapshots, while the Rust control copies its growing prefix on every append. It has the same output and checksum, but the storage strategy is not equivalent. A private compiler lowering now builds the proven append loop geometrically and materializes the immutable view once. In a separate 60-pair comparison with identical runtime, standard library and fixtures, the candidate improved Forge throughput over the frozen Forge baseline by 69.38× [45.71, 72.35] for `immutable_view` (4096 × 512); all 21 prewarm/reference checks per implementation passed. Forge/Rust throughput was 19.33 [12.59, 20.10] for the candidate, but this is not a language-level claim because the Rust control retains the prefix-copy algorithm. The ordinary `immutable` case showed no statistically clear change versus Forge baseline: 0.964× [0.927, 1.016]. Full samples, hashes and method are in the [paired baseline/candidate report](cpu-private-view-lowering-2026-10-12.json).

The focused comparison uses GCC 13.3.0 and rustc 1.98.1 on the AMD BC-250 host, with native CPU tuning, the preserved optimized Forge SDK archives, prewarmed balanced order, independent checksum references and bootstrap intervals. Full samples and source/build hashes are in [the 40-pair suite](cpu-current-all-2026-10-12.json) and [the 120-pair builder rerun](cpu-current-builder-120-2026-10-12.json).

Two follow-up probes did not improve the evidence: GCC `-fwrapv` kept LCG and primes near parity, and factor-4 LCG unrolling did not speed up Forge. Their reports remain [here](cpu-wrapv-2026-10-12.md) and [here](cpu-lcg-unroll4-2026-10-12.md).

## Source-level algorithm experiments

The compiler's guarded affine Mersenne multiply-add lowering was measured on `(value*48271+1)%2147483647` over 8,000,000 iterations. In 60 balanced groups, candidate Forge reached 1.7861× [1.7614, 1.7925] baseline Forge throughput and 2.1024× [2.0864, 2.1119] Rust throughput. Every sample matched an independent affine-map exponentiation oracle. This is compiler-level evidence for one arithmetic pattern; it does not imply general 2.10× Rust performance. See the [paired report](affine-mersenne-final-2026-10-12.md) and [raw samples](affine-mersenne-final-2026-10-12.json).

The range-guarded Mersenne-fold LCG variant is a verified workload-specific result above the threshold: candidate Forge processed the measured LCG workload 1.1563× [1.1506, 1.1590] as fast as the unchanged Rust control, and 1.1464× [1.1419, 1.1488] as fast as baseline Forge. It checks that the seed is in `[0, 2147483647)` and retains the original wrapping multiply and signed remainder loop for every other seed. The proof and 60-pair three-way measurements are in the [Mersenne-fold report](lcg-positive-mersenne-fold-2026-10-12.md). This modifies the Forge benchmark implementation and uses a workload-specific arithmetic identity; it demonstrates that this LCG implementation can pass 1.10, but it is not evidence that the compiler or arbitrary Forge programs are 1.10× Rust.

Two equivalent prime-algorithm experiments also reduce runtime without materially changing the Forge/Rust ratio. Matched wheel factorization reached 1.0074× [1.0025, 1.0103], and matched Miller–Rabin reached 1.0192× [1.0130, 1.0261]. Both speed up Forge and Rust similarly, so neither supports the 1.10 target. See the [wheel report](cpu-prime-wheel-2026-10-12.md) and [Miller–Rabin report](prime-miller-rabin-matched-2026-10-12.md).

## HTTP capacity and throughput

The prior V2 loopback test completed four one-request-per-lane bursts at 28,000 configured clients for both servers. At that setting Forge delivered 9,046 successful requests/s and Rust 8,817; the paired ratio was 1.030 [0.940, 1.124]. This shows a finite tested burst, not sustained capacity or an absolute server maximum, and the interval does not establish the 1.10 target. The ephemeral-port range and the two-CPU V2 load observer also constrain interpretation. See [the V2 report](rust110-final-cpu-http-measurements-2026-10-12.md).

The separately versioned V3 single-reactor observer passed nine response/EOF/error-path tests and fresh smoke validation against both server binaries. Its first capacity screens were invalidated by shared-host network pressure: one trial recorded 511 connect timeouts after conntrack reached 262,144/262,144; a lower-concurrency rerun recorded 64 timeouts as the same shared table filled. After pressure subsided, a clean 8-pair rerun at 64 sockets completed all 4,000 requests in every measured sample with zero errors. It measured 8,591.7 Forge req/s and 8,556.6 Rust req/s, with paired Rust/Forge throughput ratio 1.0046 [0.7070, 1.0254]. The client reactor spent about 0.40–0.46 s in system CPU time during most 0.4–0.5 s samples, so the observer was near its one-core limit; these numbers do not establish server-only throughput, an absolute maximum, or the 1.10 target. The largest configured burst remains V2's 28,000 clients, which is a tested point rather than an absolute capacity limit. See the [V3 rerun report](http-v3-clean-4w64c-2026-10-12.md), [machine-readable measurements](http-v3-clean-4w64c-2026-10-12.json), and [raw attempts archive](http-v3-clean-4w64c-2026-10-12.raw.tar.gz).

The failed V3 reports and per-request diagnostics remain preserved in [the high-concurrency report](http-v3-screen-high-2026-10-12.json), [the lower-concurrency report](http-v3-screen-low-2026-10-12.json) and [the earlier raw runs archive](http-v3-screen-runs-2026-10-12.raw.tar.gz). The runner reports observer footer counts and the first failed request explicitly; failed samples are excluded from throughput claims.

## What the evidence supports

Forge exceeds Rust's measured throughput by at least 10% on the checked scan, ownership-returning builder, and compiler-optimized LCG workloads on this host. The unchanged LCG baseline, prime-search controls, and matched prime-algorithm experiments remain below target. The current HTTP result does not prove a 10% advantage or an absolute capacity. The private immutable-view optimization passes semantic, ABI and self-host checks and substantially improves its Forge baseline, while remaining outside the Rust-matched target summary because the Rust storage strategy differs. These results are workload-specific, not a language-wide performance guarantee. HTTP capacity still needs an isolated or otherwise clean host for decision-grade measurements.

## New code-generation and mailbox measurements (2026-10-12)

A dense integer `match` lowering was reviewed as a possible compiler optimization. The current emitter in `compiler/codegen.c:1966-2001` writes an `if / else if` equality chain. A 64-arm Forge fixture with distinct constant results generated that chain, but GCC `-O3 -march=native` lowered the generated function into a bounds check and indexed constant-table load (`CSWTCH.12`). A separate C control with 64 dense equality arms and distinct external no-inline calls lowered to a jump table (`jmp *`). This is code-generation evidence only, not a Forge/Rust performance measurement; sparse matches and more complex arm bodies may compile differently. It does not justify adding a separate switch transform without an end-to-end paired result.

Actor mailbox traffic was previously absent from the complete-lifecycle coroutine comparison. A focused native-thread bounded queue comparison is now recorded below. It shows a throughput advantage for Forge in this fixture, but does not isolate the `fr_send` broadcast cost; testing a wakeup change still needs an independent before/after runtime comparison.

No implementation change follows from these probes. All CPU, coroutine, HTTP and mailbox results remain scoped to their individual workloads; none establishes a general language-wide performance guarantee.

### Mailbox throughput probe

A dedicated bounded-queue comparison now measures 1 producer and 1, 4, or 16 blocking consumers over 1,000,000 integer message IDs. Both queues have capacity 256, use a mutex and condition variable, broadcast after each accepted message, and retry when full; the Forge side calls `fr_send`/`fr_recv` directly from native threads, and the Rust control uses `Mutex<VecDeque>`/`Condvar`. Startup is outside the timed region, while message transfer and stop sentinels are inside it. Every run checked all IDs exactly once and matched the independent sum `499999500000`. Ten alternating-order pairs completed per consumer count with zero integrity failures.

| Receivers | Forge median messages/s | Rust median messages/s | Forge/Rust throughput ratio (paired median, bootstrap 95% interval) |
| ---: | ---: | ---: | ---: |
| 1 | 3,073,606 | 1,647,782 | 1.875 [1.754, 2.795] |
| 4 | 1,612,173 | 891,082 | 1.850 [1.632, 1.952] |
| 16 | 684,038 | 348,786 | 1.977 [1.941, 2.021] |

These results exceed 1.10 for this bounded mailbox fixture. The single-consumer interval is wide because several Forge samples ran at roughly twice its usual rate, so the median is more reliable than a point estimate and the interval signals substantial host variability. This is an API/runtime comparison, not a general language benchmark: Forge uses its runtime's ring and pthread primitives while the Rust control uses the standard library's queue and synchronization primitives. It identifies no urgent `fr_send` broadcast regression; it does not isolate broadcast cost or establish capacity for other actor workloads. A paired bootstrap over 30,000 resamples produced the intervals shown. Raw samples and checks are in [the 10-pair CSV](mailbox-forge-rust-2026-10-12.csv); reproduce with `benchmark/mailbox/run.py --pairs 10`.

The measurement used Forge runtime commit `e3eb0089bdc9760d0d6fbaadd4d9fde0f17f26fe`, GCC 13.3.0, rustc 1.98.1, and the AMD BC-250 host. Both implementations were built with release optimization; the Rust control uses thin LTO and one codegen unit. No runtime implementation change was made.

### Coroutine scaling beyond four physical workers

The complete-lifecycle runner and result observer now accept arbitrary positive worker counts up to the available physical-core count; the measured worker sets are `[0, 2, 4]` and `[0, 2, 4, 6, 8, 10]`. A 12-pair, order-balanced sweep at 3 and 6 workers passed every per-task reference check. The scheduler-heavy and reduction-budget-crossing cases remained above 1.10 in both configurations, while mixed CPU stayed below the target at 3 workers and was inconclusive at 6. A focused 32-pair rerun of the 6-worker mixed-CPU case measured Forge/Tokio throughput ratio 0.9560 [0.8996, 1.0592], below 1.10; Forge's displayed median was 68.081 ms versus Tokio's 62.606 ms. Thus adding physical workers does not close this mixed CPU gap on this host. The [12-pair sweep](coroutine-workers-3-6-final-2026-10-12.md), [32-pair focused result](coroutine-mixed-cpu-6w-32pairs-2026-10-12.md), and their raw JSON preserve conditions and measurements. The earlier loaded screen is retained separately and excluded from these claims.

This is a supported worker-configuration result, not evidence that scheduler changes would improve the case: the 3/6-worker sweep only changes measurement configuration and validator bounds. It does not alter Forge or Tokio dispatch policy. The 6-worker mixed-CPU row's 95% interval is wholly below 1.10, while it overlaps parity, so the scoped conclusion is that this exact workload/configuration misses the goal, not that all multi-core coroutine workloads do.

## Runtime follow-up measurements (2026-10-12)

The Linux event-loop burst test compares the selected 256-entry batch with the 64-entry baseline and direct Rust `epoll_wait`. Forge's paired median reached 0.9933× Rust at 256 ready descriptors and 0.9876× at 1,024; at 4,096 it measured 1.0125×, with a wide 95% interval [0.9755, 1.0967]. The sampled cases do not establish the 1.10 target. Capacity 256 reduced repeated polls without materially changing the 64-ready-fd case; capacity 1,024 was rejected for regressing small bursts. This is a burst-drain microbenchmark, not application or scheduler throughput. See the [capacity decision](event-batch-results-2026-10-12.md), [selected run and raw measurements](event-batch-256-adopted-48-2026-10-12.md), and [rejected 1,024-entry run](event-batch-1024-48-2026-10-12.md).

A separate experiment moved coroutine queue dequeue and work stealing outside the scheduler-wide mutex. In the 32-pair complete-lifecycle comparison, the 4-worker scheduler-heavy case improved 1.2524× [1.0437, 1.4665], but the mixed-CPU case was 1.0005× [0.9501, 1.0410] and the reduction-budget-crossing case was 0.9652× [0.8336, 1.1748]. Single-worker mixed CPU measured 0.9972× [0.9951, 0.9993]. The result is workload-dependent and does not establish a reliable general gain; the candidate patch was rejected and is not in the runtime checkout. The [decision report](coroutine-scheduler-lockscope-decision-2026-10-12.md) links both paired runs, raw measurements, and the exact candidate patch.

The selected runtime and matching stdlib are now the clean-CMake defaults in Forge (`9ece48e` pins runtime `0b1e7d4e6ae0996422553666e349fc40f11e3ac6` and stdlib `a16cf1bf1fe81c92f64aa6df675a353674715c98`). A fresh release configure/build, including the stage2 self-host target, passed all 22 CTest tests. This integrates the measured event-loop implementation into default consumer builds; it does not change the benchmark ratios above.

A follow-up combined out-of-lock coroutine dequeue with batched terminal-state commits (up to 32 completions per scheduler-lock acquisition). The runtime's four CTest tests passed. In 32 balanced, complete-lifecycle pairs, the 4-worker scheduler-heavy case improved 1.1339× [1.0395, 1.2905], but 4-worker mixed CPU regressed to 0.9626× [0.8983, 1.0444] and budget-crossing to 0.8552× [0.8092, 1.0170]. Single-worker results stayed near parity except a small budget-crossing regression. Since the gain is workload-specific, its interval does not establish even a 1.10× improvement over the baseline, and two cases regressed, the candidate was rejected and removed from the runtime checkout. The [32-pair result](coroutine-completion-batch-32pairs.md) and [raw samples](coroutine-completion-batch-32pairs.json) preserve details and artifact hashes; Rust was a correctness/measurement control, not the ratio denominator.

A read-only subagent review proposed sharing the decomposition of `value - 1` across Miller–Rabin bases 2 and 3. In 120 balanced groups, the matched candidate passed 175 independent-reference cases plus 480 prewarms and 480 measurements, but Forge improved only 1.0021× [0.9993, 1.0042] over its previous Miller–Rabin implementation. The matched Rust candidate improved 1.0052× [1.0017, 1.0079], leaving candidate Forge/Rust at 1.0173 [1.0136, 1.0230]. The shared-decomposition change was rejected; the [decision report](prime-mr-shared-decomp-120-2026-10-12.md) and [raw samples](prime-mr-shared-decomp-120-2026-10-12.json) retain code and measurements.
