# Forge performance against the Rust control: current evidence

Status: compiler optimization and paired validation are complete for the private immutable-view append case. For equal work, this report uses Rust elapsed time divided by Forge elapsed time; a ratio of 1.10 means Forge processed at least 110% as much work per second for that workload. Results are scoped to the named fixture, host, compiler versions and measurement protocol.

## Source-matched CPU results

| Workload | Dimensions | Forge median | Rust median | Rust elapsed / Forge elapsed (95% interval) | Evidence |
| --- | ---: | ---: | ---: | ---: | --- |
| Checked byte scan | 131,072 × 512 | 37.830 ms | 85.964 ms | 2.2727 [2.2642, 2.2884] | 40 balanced pairs; supports ≥1.10 on this case |
| Reserved string builder | 32,768 × 1,024 | 69.367 ms | 94.195 ms | 1.3607 [1.3099, 1.3812] | 120 balanced pairs; supports ≥1.10 on this case |
| LCG | 250,000 × 64 | 60.729 ms | 61.032 ms | 1.0051 [0.9998, 1.0092] | 40 balanced pairs; near parity |
| LCG (Mersenne codegen) | 250,000 × 64 | 40.591 ms | 61.027 ms | 1.5041 [1.5001, 1.5068] | 120 balanced pairs; supports ≥1.10 on this case |
| Prime search | 2,000 × 128 | 74.796 ms | 75.736 ms | 1.0111 [1.0094, 1.0130] | 40 balanced pairs; below target |

The scan, reserved builder, and compiler-optimized LCG cases are source-matched results above the target. The LCG candidate changes only compiler lowering; the Forge and Rust fixtures, runtime inputs, artifacts, and timing protocol remain matched. The builder creates identical bytes, reserves the same requested capacity, returns the owned buffer, scans it and cleans up within the timed rounds. Forge uses `str_builder_finish_take`; Rust returns the `String` by move. Neither clones the completed buffer. A prior 40-pair all-workload builder interval crossed 1.10, so the focused 120-pair rerun is the decision-grade result for that row.

The LCG compiler rule recognizes a local integer expression `x * C % (2^k - 1)` with positive constant `C < 2^k - 1`. It uses the Mersenne fold only when the runtime value is in `[0, M)` and the product is proven to fit signed `int64`; otherwise generated code keeps Forge's wrapping multiply and signed remainder. The original LCG source is unchanged. The 120-pair final comparison measured 1.5041× [1.5001, 1.5068] Rust throughput and 1.4962× [1.4931, 1.4985] baseline Forge throughput. Twenty-one independent-reference cases passed across the three binaries, along with all 360 checked prewarms and 360 measurements. The [detailed comparison](lcg-mersenne-codegen-120-2026-10-12.md), [raw samples](lcg-mersenne-codegen-120-2026-10-12.json), and [frozen build artifacts](lcg-mersenne-codegen-120-2026-10-12.artifacts.tar.gz) preserve the result. A separate fixed-seed diagnostic measured no material slowdown on negative seeds outside the fast range; its [checks and samples](lcg-mersenne-seed-fallback-diagnostic-2026-10-12.json) keep that claim scoped to three seeds on this host.

The remaining prime-search gap is in the dynamic division instruction: the current Forge GCC/LTO binary already removes the checked helper's zero/overflow branches from the hot loop, while Rust emits a 32-bit unsigned divide path with a 64-bit fallback. The [prime modulo assembly audit](prime-modulo-codegen-audit-2026-10-12.md) records this static comparison and rejects checked-helper elimination as a no-op for this workload. Existing runtime narrowing guards regressed, so no replacement has been adopted.

A new prototype amortized the unsigned-32-bit range test over the full prime-search call, cloned the loop for that path and kept the 64-bit fallback for other inputs. It emitted the intended narrow divides but measured 0.9905× [0.9881, 0.9914] candidate/baseline Forge throughput over 120 balanced pairs, so the versioning approach was rejected. The [probe report](prime-function-versioned-2026-10-12.md) preserves the range proof and checks.

The experimental immutable-view row remains excluded from the source-matched Rust target summary: Forge uses cached-length immutable views with arena snapshots, while the Rust control copies its growing prefix on every append. It has the same output and checksum, but the storage strategy is not equivalent. A private compiler lowering now builds the proven append loop geometrically and materializes the immutable view once. In a separate 60-pair comparison with identical runtime, standard library and fixtures, the candidate improved Forge throughput over the frozen Forge baseline by 69.38× [45.71, 72.35] for `immutable_view` (4096 × 512); all 21 prewarm/reference checks per implementation passed. Forge/Rust throughput was 19.33 [12.59, 20.10] for the candidate, but this is not a language-level claim because the Rust control retains the prefix-copy algorithm. The ordinary `immutable` case showed no statistically clear change versus Forge baseline: 0.964× [0.927, 1.016]. Full samples, hashes and method are in the [paired baseline/candidate report](cpu-private-view-lowering-2026-10-12.json).

The focused comparison uses GCC 13.3.0 and rustc 1.98.1 on the AMD BC-250 host, with native CPU tuning, the preserved optimized Forge SDK archives, prewarmed balanced order, independent checksum references and bootstrap intervals. Full samples and source/build hashes are in [the 40-pair suite](cpu-current-all-2026-10-12.json) and [the 120-pair builder rerun](cpu-current-builder-120-2026-10-12.json).

Two follow-up probes did not improve the evidence: GCC `-fwrapv` kept LCG and primes near parity, and factor-4 LCG unrolling did not speed up Forge. Their reports remain [here](cpu-wrapv-2026-10-12.md) and [here](cpu-lcg-unroll4-2026-10-12.md).

## Source-level algorithm experiments

The range-guarded Mersenne-fold LCG variant is a verified workload-specific result above the threshold: candidate Forge processed the measured LCG workload 1.1563× [1.1506, 1.1590] as fast as the unchanged Rust control, and 1.1464× [1.1419, 1.1488] as fast as baseline Forge. It checks that the seed is in `[0, 2147483647)` and retains the original wrapping multiply and signed remainder loop for every other seed. The proof and 60-pair three-way measurements are in the [Mersenne-fold report](lcg-positive-mersenne-fold-2026-10-12.md). This modifies the Forge benchmark implementation and uses a workload-specific arithmetic identity; it demonstrates that this LCG implementation can pass 1.10, but it is not evidence that the compiler or arbitrary Forge programs are 1.10× Rust.

Two equivalent prime-algorithm experiments also reduce runtime without materially changing the Forge/Rust ratio. Matched wheel factorization reached 1.0074× [1.0025, 1.0103], and matched Miller–Rabin reached 1.0192× [1.0130, 1.0261]. Both speed up Forge and Rust similarly, so neither supports the 1.10 target. See the [wheel report](cpu-prime-wheel-2026-10-12.md) and [Miller–Rabin report](prime-miller-rabin-matched-2026-10-12.md).

## HTTP capacity and throughput

The prior V2 loopback test completed four one-request-per-lane bursts at 28,000 configured clients for both servers. At that setting Forge delivered 9,046 successful requests/s and Rust 8,817; the paired ratio was 1.030 [0.940, 1.124]. This shows a finite tested burst, not sustained capacity or an absolute server maximum, and the interval does not establish the 1.10 target. The ephemeral-port range and the two-CPU V2 load observer also constrain interpretation. See [the V2 report](rust110-final-cpu-http-measurements-2026-10-12.md).

The separately versioned V3 single-reactor observer passed nine response/EOF/error-path tests and fresh smoke validation against both server binaries. Its first capacity screens were invalidated by shared-host network pressure: one trial recorded 511 connect timeouts after conntrack reached 262,144/262,144; a lower-concurrency rerun recorded 64 timeouts as the same shared table filled. After pressure subsided, a clean 8-pair rerun at 64 sockets completed all 4,000 requests in every measured sample with zero errors. It measured 8,591.7 Forge req/s and 8,556.6 Rust req/s, with paired Rust/Forge throughput ratio 1.0046 [0.7070, 1.0254]. The client reactor spent about 0.40–0.46 s in system CPU time during most 0.4–0.5 s samples, so the observer was near its one-core limit; these numbers do not establish server-only throughput, an absolute maximum, or the 1.10 target. The largest configured burst remains V2's 28,000 clients, which is a tested point rather than an absolute capacity limit. See the [V3 rerun report](http-v3-clean-4w64c-2026-10-12.md), [machine-readable measurements](http-v3-clean-4w64c-2026-10-12.json), and [raw attempts archive](http-v3-clean-4w64c-2026-10-12.raw.tar.gz).

The failed V3 reports and per-request diagnostics remain preserved in [the high-concurrency report](http-v3-screen-high-2026-10-12.json), [the lower-concurrency report](http-v3-screen-low-2026-10-12.json) and [the earlier raw runs archive](http-v3-screen-runs-2026-10-12.raw.tar.gz). The runner reports observer footer counts and the first failed request explicitly; failed samples are excluded from throughput claims.

## What the evidence supports

Forge exceeds Rust's measured throughput by at least 10% on the checked scan, ownership-returning builder, and compiler-optimized LCG workloads on this host. The unchanged LCG baseline, prime-search controls, and matched prime-algorithm experiments remain below target. The current HTTP result does not prove a 10% advantage or an absolute capacity. The private immutable-view optimization passes semantic, ABI and self-host checks and substantially improves its Forge baseline, while remaining outside the Rust-matched target summary because the Rust storage strategy differs. These results are workload-specific, not a language-wide performance guarantee. HTTP capacity still needs an isolated or otherwise clean host for decision-grade measurements.
