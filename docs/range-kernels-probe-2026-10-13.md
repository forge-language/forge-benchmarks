# Range-guarded arithmetic and scan-unroll screening

Status: correctness screening passed; performance pending. This is an explicit generated-C benchmark experiment on compiler `d4c632b`, not a shipped compiler improvement. Forge/Rust source algorithms and the Rust control remain unchanged. The runner preserves the exact original/transformed function bodies and emitted-C hashes.

The LCG prefix is taken only for 0<=seed<2147483647. Its product is at most (2147483646)*48271, below INT64_MAX. A Mersenne fold followed by at most one subtraction gives the exact remainder in [0,2147483646]; this closes the invariant for every next iteration. It therefore removes repeated range checks while retaining the original body for negative or out-of-range seeds. Nonpositive n/rounds execute zero inner work and preserve the seed, as before. Both zero-based loop increments are bounded by their signed runtime upper limits.

The modular-power prefix requires base>=0, exponent>=0 and 1<modulus<=3037000499. Each reduced factor/result is below modulus, and every product is below INT64_MAX. Unsigned products/remainder and right shifts consequently equal the original wrapping/signed operations in this guarded region. Initial base reduction still occurs even for exponent zero. Every other input reaches the original body, including division traps and negative exponents/divisors.

The Miller-Rabin helper prefix requires 1<value<=3037000499 and base>=0. The initial base>=value return is preserved. The odd decomposition starts with positive value-1, has at most 31 shifts, and calls the guarded modular power. Subsequent reduced squares satisfy the same product range; its exact decision and iteration order are preserved. Cases outside the guard retain the original body, including the original nontermination for value=1/base<1, which is deliberately excluded from executable oracle cases.

The weighted scan retains its exact loop body, wrap semantics and dependencies and requests an unroll count of 13 only. [GCC's loop pragma documentation](https://gcc.gnu.org/onlinedocs/gcc/Loop-Specific-Pragmas.html) and [Clang's loop-hint documentation](https://clang.llvm.org/docs/LanguageExtensions.html#extensions-for-loop-hint-optimizations) describe the supported hints; no independence assertion is added. A hint is not evidence of profitable code generation.

`benchmark/test_range_kernel_probe.py` checked 311 boundary, random and trap inputs against independent Python wrapping/division/Miller-Rabin references for each of original/candidate and -O0/-O3, under UBSan (1244 executions total). Inputs cover INT64_MIN/MAX, negative/zero loop bounds, negative exponents/divisors, the product-proof threshold and immediate neighbors, and checked zero/MIN%-1 failures. The source-integrity fixture also passed. Reproduce with an emitted C fixture from the pinned compiler and `python3 benchmark/test_range_kernel_probe.py --generated-c <fixture.c> --sdk <matching-sdk>`.

The hosted workflow now offers this candidate and removes the old reserved-buffer screening choices, because the current compiler already emits that transformation. Historical scripts/artifacts and pinned workflow revisions remain available for the old experiments. No performance claim is made until new reference-checked native reports complete.
